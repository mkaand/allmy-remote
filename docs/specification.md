# Technical specification — v0 design baseline

This is a design contract, not a claim of implemented functionality. Windows 11 x64 is the only initial hardware acceptance target. Other platforms remain planned. Build independently; use maintained standard libraries, OS APIs and reviewed protocol/codec implementations rather than reimplementing cryptography or adopting an existing remote desktop product.

## Core and boundaries

- Go server, React/TypeScript browser UI, SQLite WAL metadata. Build static web assets into the server distribution when practical; one runtime service, no separate frontend service or required Redis.
- Separate packages for transport, authorization, registry, session state, platform adapters and clipboard. Keep device/connection identity distinct.
- Configuration via environment or protected local files. Example origin https://remote.example.com. Local development binds loopback by default; no unauthenticated public listener.
- A reverse proxy can provide HTTPS and optional identity-aware access; application authorization remains mandatory. Trust forwarded identity only from an explicitly trusted proxy with verified assertion and audience. Keep agent authentication separate from browser login.
- Development and production use distinct configuration, data and runtime boundaries even on one machine. No live DB migration during an unvalidated build. Pin dependencies, use bounded logs, expose minimal health and readiness endpoints without private metadata. SQLite on local persistent storage; use transaction boundaries and consistent backup API for live databases.
- Initial database entities: schema migrations, operators, devices, hashed enrollment grants, hashed device credentials, session metadata, audit metadata. Never store screen frames, keypress contents or clipboard payloads. Limit retention and paginate queries.

## Sprint 1: control plane

Implement in reviewable increments:
1. Reproducible Go build and static web shell, config validation, health/readiness, graceful shutdown and tests.
2. SQLite schema and migration tests, operator authentication and secure session lifecycle.
3. One-time device enrollment, device registry and mock-device heartbeat tests.
4. Real dashboard from authorized API, offline/online state, capabilities, revoke action. No fake hardware values presented as real.

Proposed HTTP resources (versioned under /api/v1): session/login and logout, devices, enrollment grants, enrollment exchange, device revocation, and authenticated device channel. Health/readiness are separate. Every state-changing browser request requires authenticated session, origin/CSRF checks and per-operation authorization. Use opaque random credentials generated by the platform CSPRNG, hashed at rest, with expiry and revocation. Do not accept tokens in URLs; rate-limit login and enrollment. Secure, HttpOnly, SameSite session cookie; rotate at login and invalidate on logout. Use established password hashing (Argon2id or equivalent reviewed implementation) and operator bootstrap without default credentials. MFA is required before production remote access; integrate a reviewed identity provider or standard implementation.

## Agent control channel

Persistent outbound WSS, TLS validation enabled, device-specific credential; reject revoked identities. Browser never receives agent credential. Protocol version 1 negotiates capabilities, not privileges. Unknown major version fails closed. Initial message envelope fields: version, type, message ID, optional correlation ID, payload; session ID required for session traffic. Server binds source device to authenticated connection and assigns authoritative identity; never trust claimed identity in payload.

Initial message types: hello, hello_ack, heartbeat, heartbeat_ack, capability_update, error. Session messages later: request, approve/deny, start, stop, status. Schema validate all fields and reject unknown privileged actions. No generic remote command message in Sprint 1. Initial policy: heartbeat 15 seconds; offline after 45 seconds without liveness; reconnect with jittered exponential backoff capped at 60 seconds. Limits (initial adjustable policy): 64 KiB control messages, 32 queued control messages per connection; reject over-limit traffic, disconnect persistently slow consumers, never queue without bounds. No media or clipboard on this initial control-only channel. Errors contain stable codes, not secrets.

## Remote desktop milestones

Windows host begins as visible, explicitly installed interactive user-session application with start/stop and unpair controls. No service, automatic startup or elevation required for first proof of concept. OS-native capture via DXGI Desktop Duplication candidate; Windows Graphics Capture alternative. No bypass of secure desktop, screen lock, UIPI or organizational policy. Unattended access is a later explicit opt-in and security-reviewed feature, not a default.

Session state: requested -> locally approved -> active -> ended; denial, expiry, disconnect or revocation terminate the session. Start with view-only; add authorized input capability separately. One controller per session initially. Local stop always wins. Stop capture immediately on session end; release pressed input on disconnect. Consent and session status visibly shown on host. Use supported SendInput semantics only within authorized interactive session; respect keyboard layout, DPI, and monitor geometry. No keylogging.

Initial media proof of concept on a private test network: bounded full JPEG frames, one monitor, 720p/10 FPS starting profile, browser decode and display. Profile before optimizing. Use independent media transport so frame congestion cannot block control. Keep at most one pending complete frame; drop obsolete complete frames, not arbitrary delta dependencies. For dirty/move-region optimization apply move rectangles before dirty rectangles; track base frame sequence and send fresh keyframe on loss/resync. Handle rotation, cursor, display changes and capture-access loss. Adapt FPS/quality/resolution to measured congestion. H.264 and WebRTC are later candidates subject to hardware and license review. No internet-facing media until the reviewed confidentiality and authorization gates pass.

## Universal clipboard

An independent opt-in device capability, not tied to remote desktop. Default disabled until enabled locally and through authorized account/device policy. First payload text/plain UTF-8, max 64 KiB. No HTML, images, files or background browser access in first milestone. Use native clipboard change notifications where available rather than high-frequency polling. Separate clipboard transport from media; suppress self-generated writes, deduplicate event IDs, bound queues and apply a server-assigned ordering counter within an authorized sync group. Expire queued events within 30 seconds; first version drops offline events and does not replay stale content. No history by default. Each device can pause or leave a group locally. Do not silently sync corporate devices or password-manager data; exclusion is best-effort, not a perfect detector.

Before enabling real cross-device clipboard across the Internet, select a reviewed end-to-end encryption/key-management implementation and verify that the relay cannot decrypt payloads; bind sender, destination and message identity to authenticated encryption. No homemade cryptography. Device revocation excludes it from future traffic; define rekeying and failure behavior. Browser users explicitly copy/paste via permitted APIs; a browser alone cannot provide system-wide background clipboard. Headless hosts have no desktop clipboard capability.
